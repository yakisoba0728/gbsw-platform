# 관리자 기본 관리 시스템 설계

날짜: 2026-08-13
상태: 승인됨

## 범위

관리자 화면 두 개(사용자 관리·감사로그)와, 그 과정에서 드러난 계정 비활성화 결함 수정.

## 먼저: `status`가 아무것도 막지 않는다

`User.status`(`ACTIVE`/`INACTIVE`)는 스키마에만 있고 어디서도 검사되지 않는다.
Better Auth는 자체 `banned` 필드를 보므로 우리 `status`와 연결되어 있지 않다.
비활성화 기능을 만들면서 이걸 실제로 동작하게 한다.

`requireAuth()`에서 상태를 확인해 `ACTIVE`가 아니면 세션을 폐기하고 로그인으로 보낸다.
`(app)` 레이아웃이 모든 보호 화면 앞에 있으므로, **이미 로그인해 있던 세션도 다음 요청에서 끊긴다.**
로그인 직후에도 같은 레이아웃을 지나므로 비활성 계정은 화면에 들어올 수 없다.

## 사용자 관리 (`/admin/users`)

목록: 이름 · 이메일 · 역할 · 소속 · 전화번호 · 상태 · 가입일.
학생은 소속을 `1학년 3반 3번`으로 보여준다.

필터는 클라이언트에서 즉시 적용한다 — 전교생 규모(수백 명)라 전량을 넘겨도 문제없고,
초대 관리 표와 조작감을 맞춘다.

| 조치 | 동작 |
|---|---|
| 비활성화 / 활성화 | `status` 토글. 비활성 계정은 즉시 로그인 불가 |
| 비밀번호 초기화 | 임시 비밀번호 14자 발급 → 화면에 1회 표시, `mustChangePassword: true`, 다른 세션 폐기 |

임시 비밀번호는 SMTP가 없으므로 관리자가 대면·구두로 전달한다.
평문은 어디에도 저장하지 않고 화면에 한 번만 나타난다.

### 넣지 않는 것

- **역할 변경.** `학생 → 관리자`는 권한이 통째로 넘어가는 경로다. 지금 필요가 없고,
  필요해지면 확인 절차를 따로 설계한다.
- **계정 삭제.** `AuditLog.actor`가 `onDelete: Restrict`라 기록이 있는 사용자는 지워지지 않는다.
  의도된 설계이며, 비활성화가 올바른 수단이다.
- **본인 비활성화.** 관리자가 자기 계정을 잠가 스스로를 가두는 걸 막는다.

## 감사로그 (`/admin/logs`)

읽기 전용. 시각(KST) · 행위자 · 액션 · 대상 · 상세(metadata).

로그는 계속 쌓이므로 **서버에서 필터링·페이지네이션**한다(50건씩).
필터는 URL 쿼리에 실어 새로고침·뒤로가기가 자연스럽게 동작하게 한다.

필터: 액션 · 행위자 검색 · 기간(오늘 / 7일 / 30일 / 전체).

## 구조

```
src/lib/temp-password.ts          임시 비밀번호 생성
src/modules/admin-users/          admin-user.{schema,repo,service}.ts
src/modules/audit-log/            audit-log.{schema,repo,service}.ts  ← 조회 전용
src/app/(app)/admin/users/        page · 표(클라이언트) · actions
src/app/(app)/admin/logs/         page · 필터(클라이언트) · 서버 페이지네이션
```

`core/audit`은 쓰기 전용(횡단 인프라)으로 두고 조회는 모듈로 분리한다.
필터·페이지네이션은 도메인 로직이라 core에 둘 성격이 아니다.

## 테스트

**서비스** — 권한 거부 / 본인 비활성화 차단 / 상태 토글 + 감사로그 / 임시 비밀번호가 평문으로
반환되지 않고 해시로 저장되는지 / 조회 필터가 인자대로 repo에 전달되는지.

**세션 가드** — 비활성 사용자는 `requireAuth()`에서 걸러진다.

**임시 비밀번호** — 길이·알파벳·중복 없음.

## 확장 (같은 날)

### 감사로그 접속 정보

`AuditLog.ip` · `AuditLog.userAgent` 추가.

**`recordAudit()` 안에서 직접 읽는다.** 호출부가 인자로 넘기는 구조면 새 모듈이 빠뜨려도
아무도 모르게 기록만 비어버린다. 헤더 읽기는 `core/audit/request-context.ts`로 분리했다 —
`next/headers`는 요청 컨텍스트 밖(부팅 훅·스크립트·테스트)에서 못 쓰므로, 그 함수만 갈아끼우면
나머지가 그대로 돈다.

IP는 리버스 프록시를 가정해 `x-forwarded-for` 첫 항목 → `x-real-ip` 순으로 읽는다.
UA는 200자로 자른다.

### 시간 표기

`src/lib/datetime.ts` 한 곳에서만 포맷터를 만든다. 페이지마다 만들면 `timeZone`을
빠뜨리는 순간 조용히 어긋난다. 생년월일처럼 날짜만 의미 있는 값은 KST 자정(`T00:00:00+09:00`)으로
저장해 하루 밀림을 막는다.

### 사용자 상세 (`/admin/users/[userId]`)

목록의 인라인 버튼을 ⚙︎ 링크로 바꾸고 조치를 상세로 모았다.

수정 가능: 이름 · 이메일 · 전화번호 (+ 학생은 학년·반·번호·생년월일).
역할은 계속 제외한다.

### 이메일·전화번호는 필수다 (2026-08-13 변경)

처음에는 이메일을 "로그인 아이디라 못 고침"으로, 전화번호를 "비워도 됨"으로 두었다.
둘 다 뒤집는다. **모든 계정은 이메일과 전화번호를 가진다.**

- `User.phone`을 `NOT NULL`로 올렸다. 휴대폰 인증 이전에 만들어진 계정은 번호가 없어서
  마이그레이션에서 `010-0000-0000`으로 채운다. 실제 번호를 지어낼 수는 없고 비운 채로는
  제약을 걸 수 없다. 자리표시자는 관리자 화면에 그대로 보이므로 이 화면에서 고친다.
- **최초 관리자 생성에도 전화번호를 받는다.** 필수라면서 부트스트랩만 예외를 두면
  번호 없는 계정이 하나 남고, 그게 하필 교사 계정이다.
- 형식 규칙은 `lib/user-fields.ts` 한 곳에 둔다. 가입·부트스트랩·관리자 수정 세 곳이
  각자 복사하고 있었다. 표기가 어긋나면 인증 기록 대조와 변경 감지가 같이 틀어진다.

이메일을 바꿔도 로그인은 깨지지 않는다 — credential 계정은 `accountId`가 `userId`라
이메일에 묶여 있지 않다. 중복은 미리 조회하지 않고 유일 제약 위반(P2002)을 잡아서
옮긴다. 미리 검사하면 그 사이에 끼어드는 요청을 막지 못하고, 어차피 제약이 진짜 방어선이다.

`emailVerified`는 건드리지 않고 세션도 끊지 않는다. 이메일은 인증 수단이 아니며,
계정을 실제로 뺏는 경로(비밀번호 초기화·비활성화)는 각자 세션을 끊는다.

`user:update` 감사로그에는 **바뀐 항목 이름만** 남긴다 (`{ changed: ["phone", "number"] }`).
값까지 남기면 감사로그가 개인정보 사본이 된다. 바뀐 게 없으면 저장도 기록도 하지 않는다.

### 구현 중 걸린 것 두 가지

**`"use server"` 모듈은 async 함수만 export할 수 있다.** 상태 초기값 객체를 거기 두었더니
클라이언트에서 `undefined`로 들어와 `useActionState`가 빈 상태로 시작했고,
`state.changed.length`에서 런타임 오류가 났다. 상수는 `action-state.ts`(일반 모듈)로 분리했다.

**행별 액션 결과를 부모로 끌어올리지 않는다.** 자식 렌더 중 부모 `setState`는
"Cannot update a component while rendering a different component"로 터진다.
각 폼이 자기 결과를 직접 렌더한다.
