# 감사 원자성·명단 확정 검증·검증 게이트 설계

## 배경

2026-08-19 코드베이스 점검에서 다음 세 가지 신뢰성 결함을 확인했다.

1. 서비스가 업무 변경을 커밋한 뒤 `recordAudit()`를 호출한다. 감사 기록이 실패하면 사용자는 실패 응답을 받지만 업무 변경은 이미 반영되어, 감사 누락과 재시도 중복이 생길 수 있다.
2. 명단 미리보기 결과가 숨은 JSON으로 확정 경로에 돌아오며, 서버 경계가 좌석과 학생코드만 재검증한다. `name`, `birthDate`, `errors`는 조작된 미리보기 결과를 충분히 방어하지 못한다.
3. `npm run verify`가 단위 테스트만 실행하고 통합 테스트와 프로덕션 빌드를 제외한다. 저장소에 CI 워크플로도 없어 수동 부분 유일 인덱스 같은 운영 불변식이 기본 검증 경로 밖에 있다.

## 목표

- 감사 대상 업무 변경과 그 감사 로그를 하나의 데이터베이스 트랜잭션으로 커밋하거나 함께 롤백한다.
- 명단 확정 시 서버가 원본 미리보기의 오류 배열을 신뢰하지 않고 각 행을 독립적으로 정규화·검증한다.
- 빠른 로컬 검증과 완전한 검증을 명확히 분리하고, 완전한 검증을 CI에서 항상 재현한다.

## 비목표

- 초대 기반 가입의 운영 차단 문제는 이번 범위에서 수정하지 않는다.
- 감사 이벤트 이름이나 metadata의 개인정보 최소화 정책은 바꾸지 않는다.
- GitHub 배포, 브랜치 병합, 원격 푸시는 수행하지 않는다.

## 1. 감사 로그 원자성

`src/core/db/client.ts`가 애플리케이션의 트랜잭션 진입점과 재사용 가능한 데이터베이스 클라이언트 타입을 제공한다. 쓰기 저장소 함수는 선택적 트랜잭션 클라이언트를 받아, 전달되면 전역 `prisma` 대신 그 클라이언트로 모든 쿼리를 실행한다.

`recordAudit()`도 같은 선택적 클라이언트를 받는다. 행위자 이름 조회와 `AuditLog.create`는 반드시 같은 클라이언트를 사용한다. 이름 조회 실패를 `"(알 수 없음)"`으로 대체하는 기존 가용성 정책은 유지하지만, 감사 로그 생성 실패는 절대 삼키지 않는다.

서비스 계층은 권한 확인과 읽기/계획 수립을 먼저 한 뒤, 실제 업무 쓰기와 성공 감사 이벤트를 단일 interactive transaction 안에서 실행한다. 이미 내부 트랜잭션을 여는 저장소 함수는 선택적 클라이언트가 주어졌을 때 중첩 트랜잭션을 만들지 않는다. 명단 반영처럼 긴 작업은 기존 timeout을 외부 서비스 트랜잭션에도 보존한다.

성공한 업무 변경에 대응하는 감사 이벤트는 모두 원자화한다. 가입 정보 불일치로 실패 횟수가 증가하고 초대가 자동 폐기되는 경로도 실제 상태 변경이므로 조건부 감사와 함께 묶는다. 이때 사용자에게 던질 가입 실패 오류는 트랜잭션 콜백이 정상 종료된 뒤 던져야 폐기 자체가 롤백되지 않는다. 상태 변경 없이 권한 거부만 기록하는 독립 감사 이벤트는 업무 커밋과 묶을 대상이 없으므로 best-effort 단독 기록을 유지한다.

비밀번호 변경은 `auth.api.changePassword()`의 자체 커밋 바깥에 트랜잭션을 둘 수 없다. Better Auth에는 현재 세션과 현재 비밀번호 검증만 맡기고, 새 해시는 트랜잭션 밖에서 계산한다. credential hash 변경, `mustChangePassword` 해제, 현재 세션을 제외한 다른 세션 삭제, 감사 생성은 애플리케이션 Prisma 트랜잭션 안에서 직접 수행한다.

## 2. 명단 확정 경계

`rosterRowsSchema`는 다음 규칙을 서버에서 적용한다.

- 이름: 문자열 앞뒤 공백 제거 후 빈 값 금지, NFC 정규화.
- 생년월일: `YYYY-MM-DD`의 실제 존재하는 날짜만 허용하고 파서와 같은 정규형을 유지한다.
- 학생코드·학년·반·번호·학적: 현재의 형식, 범위, 재학 좌석 불변식을 유지한다.
- `errors`: 클라이언트가 보낸 값은 의사결정에 사용하지 않고, 성공적으로 검증된 확정 행의 오류 배열은 빈 배열로 정규화한다.

따라서 숨은 JSON의 `errors`를 지우거나 이름·날짜를 바꾸어도 확정할 수 없다. 액션은 스키마의 정규화된 출력만 서비스에 전달한다.

## 3. 검증 게이트와 CI

명령을 다음 의미로 나눈다.

- `npm run verify:unit`: Next 라우트 타입 생성, TypeScript, ESLint, 단위 테스트.
- `npm run verify`: `verify:unit`, 전용 테스트 DB 준비, 통합 테스트, 프로덕션 빌드.

GitHub Actions는 Node.js 24와 PostgreSQL 18을 사용한다. 단위 검증, 통합 검증, 프로덕션 빌드를 분리된 작업으로 실행해 실패 지점을 분명히 한다. 통합 작업은 빈 PostgreSQL 서비스에 `prisma migrate deploy`를 실행한 뒤 기존 통합 프로젝트 전체를 실행한다. 이 경로가 수동 SQL로 만든 부분 유일 인덱스까지 새 DB에 설치되고 테스트되는지를 계속 보장한다.

## 검증 기준

- 감사 생성 실패를 의도적으로 일으킨 실제 DB 통합 테스트에서 대표 업무 변경도 남지 않는다.
- 가입 자동 폐기와 비밀번호 변경 같은 특수 경로가 부분 커밋을 만들지 않는지 테스트한다.
- 감사 대상 성공 쓰기 경로가 모두 트랜잭션 클라이언트를 공유하는지 단위·정적 검토로 확인한다.
- 조작된 이름, 존재하지 않는 날짜, 신뢰할 수 없는 `errors`를 명단 스키마 테스트로 고정한다.
- `verify:unit`, 통합 테스트, 프로덕션 빌드가 각각 통과한다.
- CI YAML과 README 명령 설명이 실제 스크립트와 일치한다.
