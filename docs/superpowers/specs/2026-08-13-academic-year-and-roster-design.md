# 학년도와 명단 일괄 관리 설계

날짜: 2026-08-13
상태: 승인됨

## 범위

학년도 개념 도입, 명단 파일(CSV·xlsx) 일괄 등록, 학생 표 내 직접 편집.

세 가지는 순서가 있다. **학년도 모델이 나머지 둘의 전제**다. "어느 학년도의 소속인가"가
정해지기 전에 일괄 편집과 업로드를 만들면 나중에 갈아엎게 된다.

## 지금 구조의 한계

`SchoolClass`는 `@@unique([grade, classNo])`라 "1학년 3반"이 해마다 같은 행을 재사용한다.
`StudentProfile.classId`와 `number`는 현재 소속 하나만 들고 있어서, 학생이 2학년이 되면
1학년 때 소속이 덮여 사라진다. 상벌점이 붙으면 학년도별·반별 집계를 낼 수 없고
졸업생은 몇 반이었는지조차 알 수 없다.

## 데이터 모델

```
AcademicYear   year Int @unique · isCurrent Boolean
SchoolClass    year · grade · classNo            @@unique([year, grade, classNo])
Enrollment     studentProfileId · year · classId? · number? · status
                                                 @@unique([studentProfileId, year])
                                                 @@unique([classId, number])
StudentProfile id · userId · birthDate           (classId · number 제거)
```

`StudentProfile.id`는 학생의 영구 식별자로 그대로 둔다. 소속은 `Enrollment`가 학년도마다
한 줄씩 쌓는다. "현재 소속"은 `year = 현재 학년도`인 행이다.

반이 잘못 올라갔으면 그 줄만 고치면 지난 통계까지 함께 바로잡힌다. 기록마다 소속을
복사해 넣는 방식이었다면 전부 찾아 고쳐야 한다.

`classId`와 `number`는 `재학`일 때만 채운다. 졸업·자퇴한 학생에게 반과 번호는 의미가 없다.
그래서 둘 다 nullable이고, **`재학`인데 둘 중 하나라도 비면 오류로 잡는다.**

`@@unique([classId, number])`가 "한 반에 같은 번호 둘"을 막는다. Postgres는 NULL을 서로
다른 값으로 보므로 비재학 행끼리는 이 제약에 걸리지 않는다 — 의도한 동작이다.

`year`가 `SchoolClass`와 `Enrollment` 양쪽에 있는 건 중복이지만 일부러 둔다.
`@@unique([studentProfileId, year])`로 "한 학생은 한 학년도에 한 줄"을 DB가 직접 막게 하려면
`Enrollment`에 `year`가 있어야 한다. 애플리케이션 검사에만 맡기면 동시 요청에서 뚫린다.

### 학적 (`Enrollment.status`)

학생의 영구 속성이 아니라 **그 학년도의 상태**다. 같은 학생이 2026학년도엔 재학,
2027학년도엔 졸업으로 남는다.

| 저장값 | 엑셀 표기 | 뜻 | 계정 |
|---|---|---|---|
| `ENROLLED` | 재학 | 정상 | 활성 |
| `GRADUATED` | 졸업 | 과정 수료 | 비활성 |
| `WITHDRAWN` | 자퇴 | 본인 의사 | 비활성 |
| `EXPELLED` | 퇴학 | 징계 | 비활성 |
| `TRANSFERRED` | 전출 | 타교 전학 | 비활성 |
| `DEFERRED` | 유예 | 학업 중단, 복학 가능 | 비활성 (복학 시 되살림) |

DB에는 영문 상수를 넣고 화면 표기는 라벨 맵으로 둔다 — `role`·`status`가 이미 그 방식이다
(`ROLE_LABELS`). 한글은 엑셀 열의 표기일 뿐이라 파서가 상수로 옮긴다.

비활성은 로그인만 막는다. **기록은 지우지 않는다.** 상벌점·감사로그가 남아야 하고,
`AuditLog.actor`가 `onDelete: Restrict`라 애초에 계정이 지워지지도 않는다.

졸업도 비활성이다. 재학생만 쓰는 시스템이라 졸업생이 들어와도 볼 게 없고,
계정이 살아 있으면 관리 대상만 늘어난다.

## 명단 업로드

```
학년도 선택 → 파일 업로드 → 서버 파싱·검증 → 미리보기 → 확정 → 트랜잭션 반영
```

**미리보기가 핵심이다.** 200명을 되돌릴 수 없이 반영하면 안 된다. 미리보기 단계에서는
아무것도 저장하지 않고 행을 다섯으로 나눠 보여준다.

| 분류 | 내용 |
|---|---|
| 신규 | 초대코드가 발급될 학생 |
| 재배정 | 1학년 3반 12번 → 2학년 1반 7번 |
| 학적변동 | 졸업 · 자퇴 · 퇴학 · 전출 · 유예 |
| 확인 필요 | 이름+생년월일이 여럿과 겹쳐 자동으로 못 잇는 행 |
| 오류 | 형식 · 반 안에서 번호 중복 · 없는 학적 값 |

**오류가 하나라도 있으면 확정을 막는다.** 절반만 반영되는 게 제일 나쁘다.

확정은 한 트랜잭션에서 그 학년도의 기존 배정을 지우고 새로 넣는다.
`@@unique([classId, number])` 때문에 번호가 잠시 겹치는 중간 상태가 생기면 안 된다.

미리보기와 확정 사이 상태는 서버에 저장하지 않는다. 정규화된 행을 클라이언트가 들고 있다가
확정 때 되보내고, **서버가 확정 시점에 전부 다시 검증한다.** 중간에 손대도 검증을 통과해야
하고, 관리자는 어차피 표에서 직접 고칠 수 있으므로 권한 범위를 넘지 않는다.
임시 테이블을 두면 방치된 행을 청소하는 문제가 따라온다.

신규 학생분은 초대코드가 함께 생기고, 끝나면 **코드 목록을 CSV로 내려받아** 반별로 배부한다.
계정을 직접 만들지 않는 이유는 이메일·전화번호가 필수인데 학교 명단에는 그 둘이 없기 때문이다.
초대코드로 가면 학생이 가입하며 본인이 입력하고 인증까지 거친다.

### 학생 매칭

명단에 학번이 없으므로 `이름 + 생년월일`로 기존 학생을 찾는다. 둘 다 같은 학생이 여럿이면
**자동으로 잇지 않고** "확인 필요"로 빼서 관리자가 지정한다. 동명이인이 생일까지 같을 확률은
낮지만 0이 아니고, 잘못 이으면 남의 상벌점이 붙는다.

### 명단에서 빠진 학생

추측하지 않는다. 학적을 안 적었다는 뜻이므로 미리보기에서 경고로 띄운다.
그대로 넘어가면 그 학년도 배정 없이 남는다.

## 표 내 직접 편집

`/admin/students` — 학년도 · 학년 · 반 필터가 붙은 표.

셀에서 바로 고치는 건 **반 · 번호 · 학적** 셋이다. 이름과 생년월일은 초대코드 대조에 쓰는
신원이라 상세 화면에서만 고친다.

여러 칸을 고친 뒤 **한 번에 저장**한다. 칸마다 즉시 저장하면 왕복이 200번이고
중간에 실패하면 어디까지 반영됐는지 알 수 없다.

감사로그는 **학생 1명당 1줄**이다. 일괄 작업이어도 나중에 "이 학생이 왜 3반이 됐지"를
추적하려면 건별이어야 한다. `metadata`에 배치 식별자를 넣어 같은 작업임을 묶어 본다.

## 파일 형식

CSV와 xlsx 둘 다 받는다. 선생님들이 받은 파일을 그대로 올릴 수 있어야 한다.

xlsx 파싱은 **`read-excel-file`**을 쓴다. MIT, 2.4MB, 활발히 배포 중이고 읽기 전용이라
필요한 만큼만 한다. `exceljs`는 21.8MB에 최신 배포가 2023년이라 뺐고,
SheetJS(`xlsx`)는 npm 배포가 끊겨 있어 쓰지 않는다.

서식 파일은 CSV로 내보낸다. 쓰기 기능이 필요 없어 파서를 읽기 전용으로 유지할 수 있다.

**서식 파일을 내려받게 한다.** 열 이름과 학적 선택지가 박힌 빈 파일이 형식 오류를 제일 많이 줄인다.

열: `이름 · 생년월일 · 학년 · 반 · 번호 · 학적`

## 권한

모두 ADMIN 전용이다 (교사=관리자, 등급 없음).

| 액션 | 쓰이는 곳 | |
|---|---|---|
| `student:manage` | 소속·학적 수정, 명단 업로드 | 기존 |
| `academic-year:manage` | 학년도 생성, 현재 학년도 변경 | 신규 |

`student:manage`는 `can.ts`에 정의돼 있지만 지금까지 `src/` 어디서도 쓰이지 않는
죽은 액션이었다. 소속·학적을 고치는 일이 곧 학생 관리이므로 새 액션을 만들지 않고
여기에 쓴다. 이름만 다른 액션이 둘 있으면 나중에 어느 쪽을 검사해야 할지 헷갈린다.

업로드는 초대코드도 만들므로 `student:manage`와 `invite:create`를 **둘 다** 확인한다.

감사 액션: `academic-year:create` · `academic-year:set-current` ·
`enrollment:import`(배치 요약 1건) · `enrollment:update`(학생별).

## 마이그레이션

이관 대상은 학생 1명이다 (김동혁 · 1학년 3반 3번).

1. `AcademicYear` 2026 생성, `isCurrent = true`
2. 기존 `SchoolClass`에 `year = 2026` 채우고 유일키를 `(year, grade, classNo)`로 교체
3. 기존 `StudentProfile.classId`·`number`를 `Enrollment`로 옮긴다 (`status = 재학`)
4. `StudentProfile`에서 `classId`·`number` 제거

`Invite.metadata`의 학생 사전등록 값(`grade`·`classNo`·`number`)은 그대로 둔다.
가입 시점에 대조하는 값이고 학년도가 바뀌기 전에 쓰이므로 이관할 것이 없다.
다만 가입 완료 시 `StudentProfile` 대신 **현재 학년도의 `Enrollment`를 만들도록** 고쳐야 한다.

## 구조

```
src/modules/academic-year/    academic-year.{schema,repo,service}.ts
src/modules/enrollment/       enrollment.{schema,repo,service}.ts
                              roster.parse.ts    파일 → 정규화된 행
                              roster.plan.ts     행 + 현재 상태 → 분류 결과
src/app/(app)/admin/students/ page · 표(클라이언트) · actions
src/app/(app)/admin/students/import/  업로드 · 미리보기 · 확정
```

파싱과 분류를 서비스에서 분리한다. 둘 다 순수 함수라 DB 없이 테스트할 수 있고,
분류 규칙이 이 기능에서 제일 많이 바뀔 부분이다.

## 테스트

**파싱** — 열 누락 · BOM · 빈 줄 · 숫자로 읽힌 생년월일 · 없는 학적 값.

**분류** — 신규/재배정/학적변동이 제대로 갈리는지, 같은 반 번호 중복이 오류로 잡히는지,
동명이인+같은 생일이 "확인 필요"로 빠지는지.

**서비스** — 권한 거부, 오류가 있으면 아무것도 쓰지 않는지, 확정이 트랜잭션인지,
학생별 감사로그가 남는지, 학적에 따라 계정 상태가 바뀌는지.

**마이그레이션** — 기존 소속이 `Enrollment`로 옮겨졌는지.

## 단계

순서대로 만든다. 각 단계가 끝나면 동작하는 상태여야 한다.

1. **학년도·소속 모델** — 스키마·마이그레이션·가입 흐름 수정. 화면은 기존 것 그대로 동작.
2. **표 내 직접 편집** — `/admin/students`. 업로드 없이도 소속을 고칠 수 있게 된다.
3. **명단 업로드** — 파싱·분류·미리보기·확정, 초대코드 일괄 발급, 서식 파일.

2번을 3번보다 먼저 두는 이유는, 업로드가 잘못됐을 때 손으로 고칠 수단이 먼저 있어야 하기 때문이다.

## 1단계가 남긴 것 (2·3단계에서 처리)

1단계(학년도·소속 모델) 구현과 검토에서 나온, 다음 단계에 넘기는 항목들이다.

- **2단계는 학년도가 넘어가기 전에 들어와야 한다.** 지금 현재 학년도를 바꿀 화면이 없다.
  `academic-year.service`는 만들어졌지만 부르는 곳이 2단계에 있어서, 그 전에 3월이 오면
  `psql`로 직접 바꿔야 한다: `update "AcademicYear" set "isCurrent" = ("year" = 2027);`
- **`setCurrentYear`의 no-op 검사와 전환이 별도 호출이다.** 동시에 다른 연도로 전환하면
  감사로그의 `from`이 실제와 어긋날 수 있다. 데이터 무결성은 부분 유니크 인덱스가 보장한다.
  전환 화면을 붙일 때 `repo.setCurrent`가 트랜잭션 안에서 이전 연도를 반환하게 고치면 된다.
- **소속 upsert가 `status`를 건드리지 않는다** (`admin-user.repo.updateEnrollment`).
  지금은 비ENROLLED 행을 만드는 경로가 없어 도달할 수 없지만, 2단계에서 학적을 표에서
  고칠 수 있게 되면 "졸업인데 반·번호가 채워지는" 조합이 생긴다. 학적 편집과 함께 처리한다.
- **`currentEnrollment` select에 `status`가 이미 들어 있다.** 아직 아무도 쓰지 않는다 —
  2단계에서 표에 학적을 띄울 때 쓴다.
- **`keepsAccountActive()`도 아직 호출부가 없다.** 학적을 바꾸는 경로(2·3단계)가 생길 때
  계정 상태와 연결한다.

## 2단계가 남긴 것 (3단계에서 처리)

- **번호 교환과 일괄 재번호는 표 편집으로 할 수 없다.** A(3번)↔B(4번)를 맞바꾸면 A를 4로
  쓰는 순간 `@@unique([classId, number])`에 걸린다. **한 트랜잭션으로 묶어도 해결되지 않는다** —
  Postgres 유일 제약은 `DEFERRABLE`이 아니면 문장 단위로 검사한다.
  위의 "확정은 기존 배정을 지우고 새로 넣는다"가 바로 이 문제의 답이며, 3단계에서 풀린다.
- **같은 이유로, 배치 안에서 한 학생이 비운 자리를 다른 학생이 채우는 정상적 재배치도**
  2단계의 사전 충돌 검사에 걸린다. 관리자는 두 번에 나눠 저장해야 한다. 3단계의
  "지우고 새로 넣기"가 들어오면 사라진다.
- **`NumberTakenError`가 `enrollment.repo`와 `admin-user.repo` 양쪽에 별개 클래스로 있다.**
  각 서비스가 자기 repo 것만 잡으므로 지금은 문제없지만, 명단 업로드가 두 경로를 다 쓰게 되면
  `instanceof`가 모듈을 건너 통하지 않아 조용히 새는 자리가 된다. 그때 하나로 합친다.
- **`setCurrentYear`의 감사로그 `from` 값이 동시 전환에서 어긋날 수 있다.** 데이터 무결성은
  부분 유니크 인덱스와 트랜잭션이 지키므로 피해는 로그 하나뿐이다. `repo.setCurrent`가
  트랜잭션 안에서 이전 연도를 반환하게 하면 끝난다.

## 3단계가 남긴 것 (다음에 손볼 때)

- **`Enrollment.id`를 다른 테이블이 FK로 참조하면 안 된다.** 명단을 반영할 때마다 그 학년도
  배정을 지우고 새로 만들므로 id가 매번 바뀐다. 상벌점이 이걸 참조하면 `Cascade`일 때
  기록이 통째로 날아가고 `Restrict`일 때 명단 반영이 영구히 실패한다.
  **상벌점은 `StudentProfile.id`를 참조해야 한다.** `roster.repo.applyRoster`의 주석에도 적어 두었다.
- **학년·반·번호 범위(1\~3 / 1\~20 / 1\~50) 상수가 `enrollment.schema.ts`에 모였지만,
  `admin-user.schema.ts`와 `invite.schema.ts`에는 아직 리터럴로 남아 있다.** 지금은 값이
  일치하지만 반이 20개를 넘는 날 한 곳만 고쳐지고 조용히 어긋난다.
- **미리보기와 확정 사이에 명단이 바뀌는 것은 막지 않는다.** 학년도 변경은 거부하지만
  다른 관리자가 그 사이 학생을 추가하면 그 학생은 화면에 안 뜬 채 배정이 사라진다.
  관리자가 한둘인 규모라 두었다. 막으려면 `existing`의 지문을 함께 보내 대조한다.
- **같은 파일을 두 번 확정하면 아직 가입 안 한 신규 학생에게 코드가 하나 더 나간다.**
  앞 코드도 계속 유효하다. 반·번호 유일 제약이 중복 계정은 막지만 미사용 코드가 쌓인다.
- **"확인 필요"(동명이인+같은 생일)를 화면에서 직접 지정하는 기능은 없다.** 지금은 확정을
  막기만 한다. 실제로 나오면 파일을 고치거나 학생 표에서 손으로 처리한다. 필요해진 뒤에 만든다.
- **`setCurrentYear`의 감사로그 `from` TOCTOU** — 1·2·3단계에서 모두 미뤘다. 영향은 로그 값
  하나이고 데이터 무결성은 부분 유니크 인덱스가 지킨다.

## 개정 (2026-08-13, 4·5단계)

명단 흐름을 "서식 받아 채우기"에서 **"전체 내려받아 고쳐 올리기"** 로 바꾼다.
파일이 곧 전교생의 완성본이고, 줄을 더하면 추가, 지우면 삭제다.

```
전체 명단 내려받기(xlsx) → 엑셀에서 수정 → 올리기 → 변경사항 미리보기 → 확정
```

### 학생코드 — 학생 식별자

`StudentProfile`에 **랜덤 영숫자 식별자**를 둔다. 계정을 만들 때 한 번 부여하고 바뀌지 않는다.
명단 파일의 첫 열이며, **학생을 알아보는 유일한 기준**이다.

이름+생년월일 매칭을 대신한다. 동명이인이 같은 생일인 경우의 "확인 필요" 분류가 통째로
사라지고, 이름을 고쳐도 같은 학생으로 이어진다.

학번(입학년도+반+번호) 형태를 쓰지 않는 이유: 1학년 반 배정을 나중에 바로잡으면 식별자가
바뀐다. 식별자는 어떤 사실도 담지 않아야 안전하다.

학생코드가 빈 줄은 **신규 학생**이다 — 초대코드가 나가고, 가입할 때 학생코드가 부여된다.

입학 당시 1학년 반·번호는 참고 열로 함께 내보낸다(가장 이른 1학년 배정에서 유도).
**올릴 때는 무시한다** — 사실은 그 학년도 배정이 정하며, 이 열은 사람이 읽기 위한 것이다.

### 행 삭제 = 계정 삭제

지운 줄의 학생은 **계정까지 지운다.** 감사로그는 남긴다.

그러려면 `AuditLog.actorUserId`를 nullable로 풀고 **행위자 이름을 기록 시점에 스냅샷**으로
박아야 한다. 지금은 `onDelete: Restrict`라 기록이 있는 계정은 지워지지 않는다.
사실 이 편이 감사로그의 정석이다 — 과거의 사실이 살아 있는 외래키에 기대면 안 된다.

`Invite.createdById`도 Restrict라 학생이 만든 학부모 코드가 삭제를 막는다.
계정을 지우기 전에 그 학생이 만든 코드를 먼저 정리한다.

**미리보기에서 가장 눈에 띄게 보여주고, 삭제가 있으면 확정에 별도 확인을 받는다.**
엑셀에서 행은 실수로도 쉽게 지워지고, 이건 되돌릴 수 없는 유일한 동작이다.

연결된 학부모 계정은 자동으로 지우지 않는다. 자녀 연결만 끊기고 계정은 남으므로,
미리보기에서 "자녀가 없어지는 학부모"로 따로 보여준다.

### 엑셀 내보내기

`write-excel-file`(1.8MB, MIT)을 쓴다. 지금 쓰는 `read-excel-file`과 같은 제작자이고
머리글 스타일·열 너비를 지정할 수 있다. `exceljs`는 21.8MB에 2023년이 마지막 배포라 뺐다.

CSV로 내보내던 세 가지(서식·전체 명단·초대코드 목록)를 전부 xlsx로 바꾼다.
읽기는 CSV도 계속 받는다.

## 4단계가 남긴 것 (5단계에서 처리)

- **행 삭제 = 계정 삭제가 아직 없다.** 지금은 명단에서 빠진 재학생을 경고로만 보여주고
  그 학년도 배정만 사라진다. 계정까지 지우려면 `AuditLog.actorUserId`를 nullable로 풀고
  행위자 이름을 기록 시점 스냅샷으로 박아야 한다(`Invite.createdById`도 Restrict라
  학생이 만든 학부모 코드를 먼저 정리해야 한다).
- **학년도 전환 직후 + 학생코드 열이 없는 파일은 막을 수 없다.** 재학생 전원의 그 학년도
  학적이 `null`이라 대조할 대상이 없다. 안내 배너가 유일한 방어선이다.
  5단계에서 "삭제 건수가 일정 수를 넘으면 별도 확인"을 넣을 때 함께 다룬다.
- **`/admin/students/import` 클라이언트 청크가 536KB(gzip 159KB)다.** 대부분은
  `@/lib/invite-code`가 모듈 최상단에서 `node:crypto`를 물어 들어온 폴리필이며
  이 브랜치가 만든 게 아니다. `formatInviteCode`를 crypto를 물지 않는 파일로 떼고
  `write-excel-file/browser`를 다운로드 핸들러 안에서 `await import()`로 늦추면 된다.
- **`exportRoster`에 감사로그가 없다.** 전교생 이름·생년월일을 파일로 빼는 동작이다.
  규칙은 쓰기에만 요구하므로 위반은 아니지만, 판단해 볼 값어치가 있다.

## 넣지 않는 것

- **자동 진급.** 명단 파일이 사실의 근거다. 시스템이 학년을 올려두고 파일과 어긋나면
  어느 쪽이 맞는지 알 수 없다.
- **학년도별 상벌점 집계 화면.** 상벌점 모듈에서 다룬다. 여기서는 집계가 가능한
  데이터 구조만 만든다.
- **되돌리기.** 미리보기로 확정 전에 막는 쪽을 택했다. 확정 후 되돌리려면 초대코드 발급과
  계정 상태까지 같이 되감아야 해서 훨씬 복잡하다.
