## 2. 항목별 처리

### DATA-USER-01 · 활성 학생 영구삭제 (`18e7e30`)

`deleteUserPermanently`가 권한·자기자신·역할·확인이름 넷만 보고 `deletedAt`을 보지
않았다. `User` → `StudentProfile` → `Enrollment`·`MeritAward`·`Pass`·`ParentStudent`가
전부 Cascade라 **재학생의 상벌점·출입증 이력 행 자체가 사라진다.**
`schema.prisma`의 `User.deletedAt` 주석이 적어 둔 보존 원칙과 어긋나 있었다.

서비스와 repo **양쪽에서** `deletedAt`을 요구하고, 화면은 삭제 표시된 계정에서만
완전 삭제 폼을 띄운다.

### AUTHZ-PASS-01 · 학생 경로의 재학 자격 (`136e686`)

올바른 구현이 이미 저장소에 나란히 있었다 — 관리자 경로는
`lockEligibleStudentForPassCreation`(역할·활성·미삭제·현재 학년도 ENROLLED)을 쓰는데
학생 신청은 `lockStudentForPassCreation`(프로필 존재만)을 썼고, 학생증 QR은
`findStudentProfileByUserId`까지만 봤다.

판정 술어를 `Prisma.sql` 조각 둘(`ELIGIBLE_USER` · `enrolledIn`)에 모으고, 쓰기
경로와 읽기 경로가 그것을 나눠 쓴다. **느슨한 함수는 지웠다** — 남겨 두면 다음
사람이 다시 집어 쓴다.

### DATA-ATT-01 · 첨부 청소의 TOCTOU (`777c4a6`, 테스트 `a1c23f6`)

`sweepMyOrphans`가 트랜잭션 **밖에서** 목록을 읽고 그 id로 삭제해, 그사이 정상 글에
붙은 첨부까지 DB 행과 파일이 함께 지워질 수 있었다.

조회를 트랜잭션 안으로 옮겨 `FOR UPDATE`로 잠그고, 삭제에도 `postId IS NULL`과
cutoff를 다시 걸어 `RETURNING`으로 **실제 지워진 행만** 감사로그와 파일 삭제 대상으로
삼는다.

### SEC-OTP-02 · 비밀키 없는 코드 해시 (`d8751c7`)

6자리는 후보가 10^6뿐이라 `codeHash` 한 줄이 곧 코드였다. `pass.token.ts`와 같은
방식으로 `BETTER_AUTH_SECRET`에서 HKDF로 키를 파생해 HMAC으로 서명한다.

### SEC-OTP-01 · SEC-REG-01 · challenge 결속 (`2c2c97d`)

`confirmCode`가 `(channel, target)`으로 최신 활성 코드를 찾아 시도 횟수를 올렸다.
이메일·전화번호는 비밀이 아니므로, **그것만 아는 제3자가 아무 6자리나 반복해 정상
가입자의 코드를 5회 만에 태울 수 있었다.** 발송도 유효한 초대만 있으면 임의의
수신처로 보낼 수 있었다.

`VerificationCode`에 불투명한 `challengeId`와 `inviteId`를 더했다. 확인은
`confirmCode(challengeId, code)`로만 닿고 대상으로 찾는 경로를 **없앴다.** 해시
서명 입력에도 challengeId가 들어가고(HKDF info v1→v2), 초대별 시간당 발송 예산을
세며, 가입 완료가 두 proof의 채널·대상·초대를 지금 가입하는 값과 대조한다.

### SEC-BOOT-01 · 최초 관리자 직렬화 (`f4ee238`)

토큰이 `globalThis`의 프로세스 메모리라 인스턴스가 둘이면 서로를 보지 못한다.
`pg_advisory_xact_lock`을 잡은 뒤 **트랜잭션 안에서** 사용자 수를 다시 센다.
콘솔 토큰의 이중 게이트는 그대로 두되, 직렬화의 책임은 DB로 옮겼다.

### SEC-PROXY-01 · 오리진 고정 (`17e9beb`)

`x-forwarded-host`·`host`·`x-forwarded-proto`를 읽어 허용 오리진 후보를 만들던 코드를
전부 없앴다. 공개 주소의 유일한 출처는 `BETTER_AUTH_URL`이다.

### AVAIL-IO-01 (일부) · 로그인 본문 상한 (`30aec39`)

`next.config.ts`의 `bodySizeLimit`은 서버 액션 전용이라 라우트 핸들러에 걸리지

### OPS-PASS-01 · 목록 절단 (`fbb4832`, `f98fdb5`)

`take: 100`/`take: 200`에 cursor가 없어 101번째 대기 신청과 201번째 활성 출입증에
도달할 수 없었다. 페이지 50건의 cursor 페이지네이션을 붙이고 상태를 URL에 둔다.

> **Prisma 주의**: `cursor` + `skip: 1`은 **커서 행이 where에서 빠지면 그 다음 한 건을
> 대신 삼킨다.** 커서 행은 곧 「교사가 방금 승인한 신청」이라 이 화면에서 흔하다.
> `skip: 0`으로 두고 맨 앞이 커서일 때만 버린다.

## 5. 배포 시 확인할 것

**`BETTER_AUTH_URL`이 실제 접속 주소와 정확히 일치해야 한다.** 이제 허용 오리진의
유일한 출처라, 포트나 https 여부가 어긋나면 **로그인이 전부 403**이 된다(fail-closed).
compose가 이 값을 필수로 강제하지만, 테스트 서버에 rsync로 올릴 때 먼저 확인한다.
공개 호스트를 둘 이상 두려면 환경변수가 아니라 코드를 고쳐야 한다.

**배포 시점의 미확인 인증번호는 전부 무효가 된다.** 코드 해시 서명 입력이 두 번
바뀌었다(비밀키 도입, challengeId 추가). 수명이 5분이라 진행 중이던 가입자가 재요청
한 번 하면 된다. `BETTER_AUTH_SECRET`을 회전할 때도 같으며, 그때는 학생증 QR도 함께
무효가 된다.

**CHECK 제약은 `NOT VALID`로 붙어 있다.** 새 쓰기만 막고 기존 행은 검사하지 않는다.
운영 데이터를 정리한 뒤 별도 마이그레이션으로 `VALIDATE`를 돌린다.
