## 2. 인증번호 무제한 발송 (`4ea2899`)

보고서가 둘로 나눈 것이 한 구멍이고, 보고서가 쓴 것보다 심했다.

코드 행은 발송 **전에** 예약으로 태어난다 — `expiresAt = createdAt`이 그 표식이다.
그런데 청소가 `expiresAt <= now`를 봤으므로 **발송이 끝나기 전에 들어온 다음 요청이
그 행을 지웠다.**

```
A: 예약 커밋 → 문자 발송 중 (수백 ms ~ 수 초) ──────────────┐
B:          요청 → A의 예약 행 삭제 → 발송 수 0 → 발송      │
C:                        요청 → B의 행 삭제 → 발송 수 0 → 발송
```

지워진 행은 **대상·초대·IP 세 한도의 계산에서 모두 사라진다.** 발송보다 빠르게
이어 부르기만 하면 되므로 동시성도 필요 없고, 초대코드 하나면 됐다. 문자는 건당
과금이다.

먼저 보낸 쪽도 손해를 본다 — 문자는 실제로 나갔는데 활성화가 대상 행을 찾지 못해
「더 최근에 요청한 인증번호를 사용해 주세요」로 끝난다. 받은 번호를 넣을 자리가 없다.

둘째 얼굴이 초대 예산이다. 잠금이 대상과 IP에만 걸려 있어, **한 초대로 수신처를
바꿔 가며 병렬 요청하면** 서로를 보지 못해 예산이 그대로 넘어갔다.

**고친 방법** — 보고서는 명시적 상태머신(RESERVED/SENT/FAILED/…)을 요구했지만
두 줄로 닫힌다.

- 청소에 **유예 60초**를 둔다. 외부 발송 상한은 SMTP·알리고 모두 10초라 넉넉하다.
  유예 안의 예약 행은 남으므로, 발송 중인 요청도 한도를 차지한 것으로 센다.
- 잠금 순서를 **대상 → 초대 → IP**로 고정한다. 순서를 고정해야 교착하지 않는다.

> **테스트가 이 파일만 mock 모드를 쓰지 않는다.** 발송이 즉시 끝나면 예약 행이 살아
> 있는 시간이 0에 수렴해 결함이 재현되지 않는다. 지연 sender를 물리고 시차를 두어
> 쏜다. 변이로 확인했다 — 유예를 빼면 6번 중 1건만 살아남고, 초대 잠금을 빼면
> 11건이 전부 통과한다.

**하지 않은 것:** 보고서의 「reservation 트랜잭션 안에서 초대를 다시 검사하라」는
받지 않았다. 문자 한 통이 더 나갈 수 있는 창을 막자고 인증 모듈을 Invite 테이블에
결속시키는 값이 아니다. 그 행은 도메인 데이터가 아니라 5분짜리 임시 데이터다.

## 5. 파일 I/O (`db22865`, `984c1af`)

보고서는 셋을 묶었다. 하나씩 크기가 달라 따로 처리했다.

### 다운로드 — 스트리밍과 Range

`readFile`이 파일 전체를 버퍼에 올렸다. 첨부는 파일당 20MB라 **동시 내려받기
수만큼 그 크기가 힙에 쌓인다.** Range도 없어 큰 PDF를 보다 끊기면 처음부터
다시 받아야 했다.

서비스가 바이트 대신 좌표(`storageKey`·`storedAt`·`size`)를 주고 라우트가
디스크에서 응답으로 흘려보낸다. `size`는 DB에 적힌 값이 아니라 `stat`이 읽은
실제 크기다 — 그래야 `Content-Range`·`Content-Length`가 응답하는 파일과 어긋나지
않고, 그 `stat`이 없는 파일을 ENOENT로 걸러 전과 같은 404를 만든다.

Range 해석은 순수 함수 하나가 맡고 **알아듣지 못하는 형태는 전부 전체 응답으로
떨어뜨린다.** Range는 서버가 무시해도 되는 요청이라, 애매한 값에 206을 붙이는
쪽이 위험하다. 시작이 파일 끝을 넘는 것만 416이다.

> 끝 경계는 **실제 파일을 써서** 확인한다. HTTP Range의 끝은 포함이고
> `createReadStream`의 `end`도 포함인데, 둘이 어긋나면 알린 길이와 보낸 바이트가
> 한 바이트 달라진다. 변이(`end - 1`)로 세 테스트가 깨지는 것을 봤다.

### 내보내기 — 행 수 상한

`take: null`로 기간 전체를 한 요청에 쏟았다. **5,000건** 상한을 두고 넘으면
기간을 좁히라고 답한다. 전교 300명이 기본 30일을 뽑으면 천 건 안쪽이라 실사용에는
걸리지 않는다.

보고서는 백그라운드 `ExportJob`을 요구했으나 학교 규모에 과하다. 상한이 실제로
걸리기 시작하면 그때 다시 본다.

### 초과 본문 — 앱이 아니라 프록시에 걸었다

보고서는 `readCappedBody`가 상한을 넘긴 뒤에도 EOF까지 읽는 것을 지적했다.
**앱 코드는 건드리지 않았다** — 그 자리 주석이 「취소하면 Node 본문 파서가 예외를
낸다」고 적고 있고, 실측 없이 되돌릴 판단이 아니다.

대신 진짜 방어선을 배포 문서에 채웠다. 크기 상한만 있고 **시간 상한이 없었다** —
상한 안의 크기를 아주 느리게 흘리는 요청은 크기 검사를 통과한다.

- nginx `client_body_timeout`·`client_header_timeout` 15초
- Caddy `servers { timeouts { read_body / read_header } }` 15초

> Caddy의 `servers`는 **전역 옵션**이라 사이트 블록에 쓰면
> `unrecognized directive: servers`로 뜨지 않는다. 처음에 그렇게 적었다가
> `caddy validate`로 확인해 고쳤고, 문서의 두 블록을 그대로 뽑아 caddy 2.11.4로
> `adapt`까지 돌려 값이 실제로 붙는 것을 봤다. nginx 블록은 이 기기에 nginx가
> 없어 문법 검증을 못 했다.

상한이 층으로 겹치는지도 확인했다 — **앱 20 MiB < Caddy 24,000,000 < nginx 24 MiB.**
프록시가 앱보다 느슨해야 앱의 판단이 살아 있다. 인증서 자동 발급 예시에 본문
상한이 빠져 있던 것도 채웠다(본문은 그것을 「반드시」라고 적고 있었다).
