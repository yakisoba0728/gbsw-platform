## 3. 확정 결함

### F-01 · 높음 · JS가 동작하지 않으면 로그인 자격정보가 URL에 실릴 수 있다

**재현**

1. Next 개발 서버가 JS chunk를 허용하지 않는 `http://127.0.0.1:3000/login`을 연다.
2. 실제 계정이 아닌 QA용 가짜 이메일·비밀번호를 입력하고 제출한다.
3. 주소가 `/login?email=…&password=…` 형태로 바뀐다.

공식 개발 주소인 `student.localhost`에서는 JS가 정상 동작해 URL이 유지되고 오류 배너가
표시된다. 그러나 로그인 폼이 `onSubmit`에만 의존하고 native `method`/`action`을 지정하지
않아, hydration 또는 JS 로딩에 실패하면 브라우저의 기본 GET 제출이 실행되는 구조다
(`src/app/(auth)/login/login-form.tsx:32-65`). 따라서 127 호스트만의 표시 문제로 한정할 수
없다. 실제 비밀번호는 재현에 사용하지 않았다.

**권장:** JS가 없어도 자격정보가 URL·기록·로그에 들어가지 않는 POST/server action 폴백을
둔다. 클라이언트 인증을 유지하더라도 native 제출은 안전하게 실패해야 한다.

### F-02 · 높음 · 일반 승인에서 입력한 「승인 메모」가 출입증 상세에 남지 않는다

**재현**

1. 교사 승인 모달의 `승인 메모 (선택)`에 QA 메모를 입력하고 승인한다.
2. 학생·학부모·교사 상세를 다시 연다.
3. 상태와 승인자는 보이지만 입력한 메모는 보이지 않는다. DB에서도 해당 Pass의
   `decisionNote`는 `null`이었다. 감사로그 metadata의 reason에는 남아 있어 바이트가 완전히
   소실되지는 않지만, 출입증 기록과 상세 화면에서는 사라진다.

원인은 일반 승인과 보호자 확인 대행이 모두 `consentNote`라는 이름을 쓰고
(`src/app/(app)/pass/decision-panel.tsx:61-70`), 서비스가 비대행 승인에서는 그 값을 Pass에
쓰지 않으면서 `decisionNote: null`을 강제로 넣기 때문이다
(`src/modules/pass/decision.service.ts:46-76`).

**권장:** 일반 승인 메모는 별도 `decisionNote`로 받아 Pass에 보존하고, 대행일 때만
`consentNote`를 쓴다. 의도적으로 감사로그 전용이라면 입력 이름과 설명을 그렇게 바꿔야 한다.

### F-03 · 중간 · 신청 오류가 나면 출입증 폼 입력값이 전부 초기화된다

외출 시작 `18:00`, 종료 `16:00`, 행선지와 사유를 입력해 제출하면 서버가 정확히
`끝나는 시각이 시작보다 빠릅니다.`를 표시한다. 그러나 오류가 표시되는 순간 날짜·시각·행선지·
사유가 모두 빈 값으로 돌아갔다.

신청 폼은 비제어 입력을 사용하면서 action state에 제출값을 보존하지 않는다
(`src/app/(app)/pass/new/request-form.tsx:20-30,48-119`). React action 완료 후 reset과 결합해
업무 검증 실패 때 사용자가 전부 다시 입력해야 한다.

**권장:** 실패 state에 제출값을 돌려주고 `defaultValue`로 복원한다. 시간 전후 관계는 제출
전에 필드 수준으로도 안내한다.

### F-04 · 중간 · 출입증 전체 내역이 역전된 기간을 그대로 적용한다

`/pass/history`에서 시작일 `2026-09-02`, 종료일 `2026-09-01`을 넣어도 URL에 그대로
적용되고 오류 없이 0건을 표시한다. 날짜 모양만 각각 검사하고 `from <= to` 교차 검증은 없다
(`src/modules/pass/pass.schema.ts:172-197`, `src/app/(app)/pass/history/page.tsx:384-416`).

**권장:** 제출 전에 종료일 최소값을 시작일로 묶고, 서버 schema에서도 역전 범위를 거부해
필드 오류를 보여 준다.

### F-05 · 중간 · 없는 최상위 주소는 앱 밖의 영문 기본 404로 떨어진다

`student.localhost:3000/qa-missing-route`는 `404 / This page could not be found.`만 표시하며
대시보드 복귀 동선도 없다. 데이터 상세에서 호출하는 `notFound()`는
`src/app/(app)/not-found.tsx` 덕분에 한국어 앱 셸 404가 정상 표시되지만, 라우트 자체가 없는
경우에는 이 경계에 들어오지 않는다.

**권장:** `src/app/not-found.tsx`를 추가해 한국어 설명과 역할별 홈 복귀 동선을 제공한다.

### F-06 · 중간 · 명단 반영 화면의 상단 제목이 시스템 이름으로 표시된다

`/admin/students/import` 본문과 metadata는 `명단 반영`이지만 상단 `<h1>`은
`GBSW 통합관리시스템`이다. 이 경로가 topbar 제목 매핑에 없어 fallback을 쓰기 때문이다
(`src/app/(app)/admin/students/import/page.tsx:5`, `src/components/app-shell/nav.ts:196-208`).

**권장:** 정확한 경로 제목을 title map에 추가하고 새 페이지가 fallback에 의존하는지 검사한다.

## 4. UI/UX·접근성 개선 항목

### U-01 · 중간 · 비활성 버튼을 「처리 중」으로 표시한다

다음은 실제 요청이 진행 중이 아닌데도 disabled 상태에서 로딩 문구를 쓴다.

- 규정 미선택: `부여하는 중…`
- 학생 명단 변경 없음: `저장 중…`
- 이미 현재인 학년도: `바꾸는 중…`
- 발급할 학생 없음: `발급 중…`

공통 `ConfirmSubmit`은 `pending` 하나로 disabled 여부와 표시 문구를 함께 결정한다
(`src/components/ui/confirm-submit.tsx:16-35,67-84`). 호출부도 업무상 비활성 조건을
`pending`에 합친다. 조건을 충족시키면 정상 활성화되므로 기능 장애는 아니지만, 독립된 두
병렬 검사에서 모두 처음에는 실제 처리 중으로 오인했다.

**권장:** `disabled`와 `pending`을 분리하고, 비활성 상태에는 원래 동사 또는 `변경 없음`처럼
이유를 표시한다.

### U-02 · 중간 · 작성 중 게시글이 이탈 경고 없이 소실된다

공지 글쓰기에서 제목·본문을 입력한 뒤 목록 링크로 이동하고 뒤로 가면 두 값이 모두 빈다.
`PostForm`에는 제출 실패 값 복원은 있지만 이탈 경고나 로컬 초안은 없다
(`src/app/(app)/community/[slug]/post-form.tsx:39-58`).

**권장:** dirty 상태에서 이탈 확인을 제공하거나, 게시판·사용자별 임시 초안을 자동 저장한다.

### U-03 · 중간 · 입력 안내와 실제 브라우저 검증 사이가 벌어져 있다

- 게시판 주소는 소문자 영문·숫자·하이픈만 된다고 안내하지만 `INVALID SLUG`도 브라우저상
  valid다. `pattern`과 즉시 오류를 추가할 수 있다.
- 게시판 글쓰기 역할은 읽기 역할의 부분집합이어야 하지만 체크박스가 독립적이다. 자동으로
  읽기를 켜거나 관계 오류를 저장 전에 보여 주는 편이 낫다.
- 벌점 경고/위험 기준은 `1~MAX` 정수라고 안내하지만 text input에 min/max/pattern이 없어
  `abc`도 제출 직전까지 허용된다.
- 여러 required 폼은 브라우저 기본 포커스 이동만 사용한다. 긴 폼에는 필드 오류와 상단 오류
  요약을 함께 두는 편이 낫다.

서버 검증은 살아 있어 잘못된 데이터가 저장된 것은 아니다. 문제는 늦은 피드백과 재입력 비용이다.

### U-04 · 중간 · 접근 가능한 이름이 중복되거나 문맥을 잃는다

- `TruncatedText`는 보이는 복사본과 `sr-only` 전문을 함께 그린다. topbar `<h1>` 안에서
  사용하면 raw text가 `대시보드대시보드`가 되고, 실제 접근성 snapshot의 route announcer도
  제목을 두 번 포함했다 (`src/components/ui/truncated-text.tsx:98-136`,
  `src/components/app-shell/topbar.tsx:121-128`). Next의 route announcer가 `textContent`를
  읽어서 생긴 것으로 추정된다. heading 전용 표현을 두거나 중복되지 않는 accessible name을
  명시해야 한다.
- 출입증 카드 링크가 같은 유형이면 모두 `외박 상세`로만 노출된다
  (`src/app/(app)/pass/pass-card.tsx:44-47`). 날짜·상태·학생 이름을 포함해야 한다.
- 게시판 설정의 읽기/쓰기 체크박스가 각각 똑같은 `학생`, `학부모`로 노출된다. `읽기 권한:
  학생`처럼 그룹 문맥을 접근 가능한 이름에 포함해야 한다.
- 벌점 기준의 교내/기숙사 폼도 `경고 기준`, `위험 기준`, `저장` 이름이 반복되고 form 자체
  이름이 없다. 트랙을 fieldset/legend 또는 aria-label로 묶어야 한다.
- 가입 정보 단계의 두 버튼이 모두 `확인`이다. `이메일 확인`, `전화번호 확인`으로 구분한다.

### U-05 · 중간 · 외박의 다음 처리 주체가 상태 문구에 드러나지 않는다

외박 신청 직후 학생·학부모 화면 모두 `승인 대기`로 표시한다. 실제 다음 단계는 보호자 확인이고,
교사는 확인 전 승인할 수 없다. 확인 뒤에야 `보호자 확인됨`으로 바뀐다
(`src/core/authz/pass-type.ts:32-37`).

**권장:** 유형과 상태를 함께 보아 `보호자 확인 대기` → `교사 승인 대기` → `승인됨`처럼
다음 행동 주체가 보이게 한다.

### U-06 · 중간 · 스캔 화면의 안내·접근성·데스크톱 배치가 약하다

카메라 허용 시 `<video>`에는 접근 가능한 이름이 없고, 정상 대기 상태의 스캔 방법·카메라
상태·재시도 안내도 없다 (`src/app/scan/scanner.tsx:176-210`). 데스크톱에서는 약 414px 정사각형
카메라가 왼쪽에 놓이고 큰 여백이 남는다.

**권장:** `학생 QR을 카메라 안에 맞춰 주세요` 안내, live status, 접근 가능한 video 이름,
권한 재시도 버튼을 제공하고 넓은 화면에서는 판정 카드/안내와 2단 구성으로 쓴다. 카메라 영상은
정상 확인했지만 실제 다른 QR의 광학 판독은 장비 입력이 없어 미검증이다.

### U-07 · 중간 · 모바일 상벌점 부여 동선과 큰 목록의 탐색 비용이 크다

- `390×844`의 `/merit`은 전체 학생 명단 뒤에 부여 폼이 있어 학생 선택 뒤 긴 스크롤이
  필요하다. 실제 전교 명단이면 더 커진다. sticky 선택 요약/부여 패널이 유용하다.
- 검색 결과가 전체 명단을 필터링하지 않고 별도 영역에 나와, 0건이어도 전체 명단은 그대로다.
  검색의 적용 범위를 명확히 해야 한다.
- 규정 선택 70개 이상, 규정별 통계와 규정 관리 70여 행이 한 화면에 이어진다. 카테고리 접기,
  고정 헤더, 페이지네이션 또는 가상화가 필요하다.
- 모바일 학생 관리 표의 반·번호·학적은 가로 화면 밖에 있지만 스크롤 힌트가 약하다.

### U-08 · 낮음~중간 · 작은 마찰을 줄일 수 있다

- 출입증 신청 확인창은 `적은 내용으로 신청합니다`만 말한다. 날짜·시각·행선지를 요약하면
  마지막 실수를 줄일 수 있다.

  disabled/aria-disabled에 준하는 표현이 필요하다.
- 글과 여러 댓글의 삭제 버튼이 모두 `삭제`다. `게시글 삭제`, `이 댓글 삭제`처럼 대상을

## 7. 최종 실행을 일부러 하지 않은 기능

다음은 화면, 입력 검증, 확인 모달과 취소까지 확인했지만 기존 개발 데이터를 크게 바꾸거나
브라우저 밖 장치가 필요해 최종 실행하지 않았다.

- 기존 계정 비밀번호 초기화·비활성화·삭제
- 기존 게시글·댓글·게시판 최종 삭제와 게시판 설정 저장
- 현재 학년도 변경, 학생 명단 파일 실제 반영, 벌점 기준 저장
- 승인된 출입증 최종 취소, 교사 바로 부여, 실제 귀교 판독
- 내보내기 파일 내용의 수동 검산, OS 인쇄 다이얼로그, 물리 QR 광학 판독

중요 로직은 격리 통합 테스트와 E2E가 함께 통과했지만, 위 항목을 실사용과 완전히 같은 조건으로
검증하려면 폐기 가능한 별도 QA seed와 카메라 입력 장치가 필요하다.

## 8. 구현 우선순위 제안

1. **P0:** 로그인 native 폴백에서 자격정보가 절대 GET으로 가지 않게 수정한다.
2. **P1:** 일반 승인 메모를 올바른 필드에 보존하고 회귀 테스트를 추가한다.
3. **P1:** 출입증 신청 실패 시 값 보존, 전체 내역 날짜 교차 검증을 묶어 고친다.
4. **P1:** `ConfirmSubmit`의 `disabled`와 `pending` API를 분리해 전 호출부 문구를 정리한다.
5. **P2:** root 404, topbar 제목 중복 announcer, 출입증 링크/권한·설정 폼 이름을 접근성
   회귀 테스트와 함께 수정한다.
6. **P2:** 게시글 초안 보호와 게시판 slug/권한, 벌점 기준의 즉시 검증을 추가한다.
7. **P3:** 출입증 상태 문구, 스캐너 안내, 모바일 sticky 부여 패널, 긴 목록 탐색, 초대코드
   복사를 순서대로 다듬는다.
