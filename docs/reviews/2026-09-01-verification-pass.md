### RL-27 · "이 테스트 전용" 학년도 8102 — 실제로는 충돌할 수 없다

**원 서술** (`2026-09-01-full-read-audit.md` RL-27): `tests/integration/roster.repo.apply-roster.integration.test.ts:17`가
주석에 "이 테스트 전용"이라고 적은 학년도 값 `AcademicYear(year: 8102)`를 다른 통합 테스트
파일도 그대로 쓴다는 것, 그래서 두 파일이 같은 기본키를 두고 경합한다는 것.

**직접 확인:** `vitest.config.mts`의 `integration` 프로젝트 설정을 열었다.

```ts
// vitest.config.mts
{
  extends: true,
  test: {
    name: "integration",
    include: ["tests/integration/**/*.test.ts"],
    env: { DATABASE_URL: readTestDatabaseUrl() },
    // 여러 테스트가 실 트랜잭션·유일 제약 경합을 검증한다 — 파일을 병렬로
    // 돌리면 서로 다른 커넥션이 같은 픽스처 정리 시점과 겹칠 수 있다.
    fileParallelism: false,
  },
},
```

`fileParallelism: false`가 명시돼 있고, 바로 위 주석이 "여러 테스트가 실 트랜잭션·유일
제약 경합을 검증한다 — 파일을 병렬로 돌리면 서로 다른 커넥션이 같은 픽스처 정리 시점과
겹칠 수 있다"고 **정확히 이 문제를 막기 위해 넣은 설정임을 밝힌다.** 두 파일은 절대
동시에 실행되지 않는다 — A파일이 `beforeAll → it들 → afterAll`(8102 삭제)까지 완전히
끝난 뒤에야 B파일이 시작되므로, 같은 값을 쓰는 두 파일이 있어도 기본키가 겹치는 시점
자체가 없다.

**판정: 기각 유지.** `tests/integration/roster.repo.apply-roster.integration.test.ts:17`의
"이 테스트 전용"이라는 주석 표현은 부정확하다(실제로 다른 파일도 8102를 쓴다) — 그 지점만
떼어 보면 지적할 만하다. 하지만 원 서술의 핵심 주장인 "PK 충돌이 난다"는 `vitest.config.mts`를
한 번도 열어 보지 않고 파일 내용 grep만으로 세운 것으로 보이며, 실제로는 설정이 그 경합
경로를 원천 차단한다. **주석 문구 부정확 지적**과 **실제 결함(충돌 발생)** 둘을 하나의
항목으로 뭉쳐 냈다는 것이 원 감사의 실수다 — 전자만 남기면 사소한 문서 정정 거리이고
낮음으로 확정할 만한 결함이 아니어서, 항목 자체를 기각하는 것이 맞다고 판단했다.

### RL-34 · 익명 가리기 미검증 경로 — 절반만 사실이다

**원 서술** (`2026-09-01-full-read-audit.md` RL-34): 익명 가리기(`toPostListItem`)를 지나는
경로 둘 — 게시판 목록(`listPostPage`)과 대시보드(`listRecentPosts`) — **다** 테스트에
하나도 안 걸려 있다는 것.

**직접 확인:** `tests/modules/community/post.service.test.ts:409-417`을 읽었다.

```ts
it("익명 게시판 목록에도 작성자가 없다", async () => {
  getReadableBySlug.mockResolvedValue(board({ anonymous: true }));
  listPosts.mockResolvedValue([row()]);

  const page = await service.listPostPage(admin, "worry", 1);

  expect(page.posts[0].author).toBeNull();
  expect(JSON.stringify(page.posts)).not.toContain("김민준");
});
```

`listPostPage`(게시판 목록)의 익명화는 **명시적으로 테스트돼 있다** — `author`가 `null`인
것과 응답 JSON에 실명이 안 실리는 것 둘 다 단언한다. 반면 `listRecentPosts`(대시보드)는
`tests/` 전체를 뒤져도 어디서도 호출되지 않는다 — 이쪽은 원 서술대로 미검증이 맞다.

**판정: 격하 유지, 낮음.** "두 경로 다 안 걸려 있다"는 원 서술은 게시판 목록 경로에
대해서는 사실이 아니다 — 절반만 맞는 주장이었다. 검증자의 격하가 옳다.

다만 이 항목은 **그 자체로는 새 정보가 아니다.** 살아남은 절반("대시보드 경로가
미검증이다")은 이미 두 문서가 독립적으로, 더 높은 심각도로 확정해 둔 것과 같은 결함이다
— `2026-08-31-codebase-audit.md`의 **C-25**("대시보드의 게시판 횡단 목록에 테스트가
0건", 중간)와 `2026-08-31-codebase-audit-deep.md`의 **D-18**("대시보드의 `listRecentPosts`가
테스트 0건 — 게시판별 익명 마스킹 배선이 검증되지 않는다", 중간)이 같은 파일
(`post.service.ts:159-190`), 같은 함수, 같은 실패 시나리오를 이미 짚었다. §5에서 세
문서에 걸친 중복으로 함께 묶는다. **읽는 사람에게 남기는 결론:** `listRecentPosts` 미검증
자체는 낮음이 아니라 C-25·D-18이 이미 매긴 중간이 현재 유효한 심각도이고, RL-34가
낮음인 것은 이 항목 자체가(게시판 목록 절반을 잘못 얹어) 새로 보탠 가치가 없기 때문이다.

## 7. 이 검증이 못 한 것

- **§5의 중복 정리는 완전한 212×212 대조가 아니다.** `-deep` §4.1의 27행과 통독 머리말의
  8건 — 두 문서가 스스로 밝힌 교차 참조를 뼈대로 삼고, 그 각각을 코드까지 열어 재확인해
  ID를 특정했다. 이 뼈대 밖에서 세 문서가 우연히 같은 결함에 도달했을 가능성은 배제하지
  못한다. 특히 **낮음 154건 대 낮음 154건**의 전수 대조는 하지 않았다 — 낮음 묶음표는
  문장이 짧고 위치만 다른 서술 방식이 많아, 기계적 grep 몇 번으로는 놓치는 쌍이 있을
  수 있다.
- **`DL-07`이 이번 212건 목록에 없다.** `-deep` 문서 §4.3(상충 2)이 명시적으로 유효
  판정한 낮음 항목("명단에서 빠진 학생"을 설명하는 화면 다섯 곳이 오늘 빠진 학생에게는
  켜지지 않는다, `-deep` 본문 692행)인데, 이번 검증에 넘어온 확정 목록에는 빠져 있다.
  212(=53+111+48)라는 총합이 정확히 맞아떨어지는 것으로 보아 검증 준비 단계에서
  `-deep`의 112건 중 1건(DL-07)이 누락된 것으로 보인다 — 이 문서를 판정하는 단계에서
  발견했을 뿐, 되짚어 검증하지는 않았다. 후속 라운드가 있다면 이 항목부터 다뤄야 한다.
- **RL-27·RL-34를 뒤집은 근거는 코드 열람에 한정된다.** `vitest.config.mts`의
  `fileParallelism: false`가 실제로 파일 간 순차 실행을 강제하는지는 설정값을 읽어
  확인했을 뿐, `npm run test:integration`을 직접 돌려 두 파일이 정말 순차로 도는
  로그를 보지는 않았다. 마찬가지로 RL-34의 살아남은 절반(`listRecentPosts` 미검증)도
  실제로 익명 게시판 글이 대시보드에 실명으로 새는 것을 재현하지는 않았다 — C-25·D-18이
  이미 그 재현을 담고 있다는 사실에 기대어 판정했다.
- **심각도 재산정은 하지 않았다.** §5에서 "중간 → 낮음"·"낮음이 현재 유효" 같은 언급은
  전부 원 문서(`-deep`)가 이미 매긴 값을 옮겨 적은 것이지, 이번 라운드가 독자적으로
  다시 매긴 것이 아니다. 클러스터 안에서 문서 간 심각도가 갈리는 자리(C-02/R-08 등)는
  더 근거가 두꺼운 쪽을 "현재 유효"로 제안했을 뿐 확정 판정은 아니다.
- **여섯 검증자의 반증 과정 자체는 이 문서가 재현하지 않는다.** 210건의 "확정" 판정은
  주어진 결과를 그대로 받았고, 그중 코드를 다시 열어 직접 대조한 것은 기각·격하 2건과
  §5·§6에 인용한 항목들뿐이다 — 210건 전부를 다시 파일 단위로 재검증하지는 않았다.
