# GBSW 통합관리시스템

경북소프트웨어마이스터고등학교의 **상벌점·학적·계정을 한곳에서 다루는 자체 호스팅 웹 서비스**.

기숙사 학교의 실제 업무 흐름 — 야간 점호 중 휴대폰으로 벌점을 주고, 학기 초 엑셀 명단으로
전교생 반 편성을 갈아끼우고, 학생이 자기 점수를 확인하고, 학부모가 자녀 기록을 열어보는 것 —
을 그대로 담았다.

| | |
|---|---|
| **규모** | TypeScript 약 2만 줄 · 화면 20개 · 도메인 모듈 10개 · DB 모델 15개 |
| **테스트** | 78개 파일 / **1,191개** (단위) + 실 DB를 쓰는 통합 테스트 |
| **대상** | 전교 200~300명 · 역할 3종 (관리자=교직원 / 학생 / 학부모) |
| **운영** | 교내 서버 자체 호스팅. 외부 SaaS 의존 없음, SMTP 불필요 |

---

## 왜 만들었나

학교에서 상벌점은 종이와 엑셀로 돌아간다. 그래서 이런 일이 생긴다.

- 담당 교사만 현황을 알고, **학생은 자기 점수를 물어봐야 안다**
- 누가 언제 왜 줬는지 남지 않아 **나중에 다투면 근거가 없다**
- 학기가 바뀌면 반 편성을 손으로 옮기다 **번호가 어긋난다**

이 시스템은 세 가지를 설계 목표로 삼았다.

1. **모든 쓰기는 흔적을 남긴다.** 부여·취소·명단 반영·권한 거부까지 감사로그로 남는다.
2. **학생과 학부모가 직접 본다.** 점수를 묻지 않아도 되게 한다.
3. **되돌릴 수 있게 한다.** 잘못 준 상벌점은 사유를 적어 취소하고, 기록은 남긴다.

## 기술 스택

| 영역 | 선택 | 버전 | 고른 이유 |
|---|---|---|---|
| 프레임워크 | **Next.js** (App Router) | 16.3 | 서버 컴포넌트로 DB 조회를 서버에 두고, 서버 액션으로 폼을 처리해 API 계층을 따로 두지 않았다 |
| 언어 | **TypeScript** | 5.x | 권한 액션·역할·상벌점 종류를 유니온 타입으로 두고 컴파일 단계에서 빠짐을 잡는다 |
| UI | **React** | 19.2 | `useActionState`로 폼 상태·대기·오류를 한 훅에서 다룬다 |
| 스타일 | **Tailwind CSS** | v4 | 디자인 토큰을 `@theme`에 두고 화면 코드는 토큰 이름만 쓴다 |
| ORM | **Prisma** | 7.9 | 드라이버 어댑터(`@prisma/adapter-pg`) 사용 |
| DB | **PostgreSQL** | 18 | 부분 유니크 인덱스로 "현재 학년도는 하나뿐"을 DB가 보장한다 |
| 인증 | **Better Auth** | 1.6 | 세션 쿠키 기반. 이메일 링크가 필요 없어 SMTP 없이 돈다 |
| 검증 | **zod** | 4.4 | 경계에서 한 번만 검증하고 서비스는 타입이 맞는 입력을 신뢰한다 |
| 테스트 | **Vitest** | 4.1 | 단위(목)와 통합(실 Postgres)을 프로젝트로 분리 |
| 엑셀 | write-excel-file / read-excel-file | — | 명단 가져오기·내보내기, 상벌점 내역 내보내기 |
| 배포 | **Docker Compose** | — | `db` → `migrate` → `app` 순서로 뜬다 |

### 쓰지 않기로 한 것

- **NestJS 분리** — 프론트/백을 쪼개는 안을 검토하고 접었다. 웹 클라이언트 하나뿐인 규모에서
  분리의 이득(독립 배포·팀 분담)은 안 나오는데 교차 출처 쿠키·HTTP 왕복·DTO 이중 관리 비용은
  그대로 든다. 대신 **업무 로직을 `service.ts`에만 두어 나중에 진입점만 갈아끼울 수 있게** 했다.
- **외부 인증 SaaS** — 학생 개인정보를 교외로 내보내지 않는다.
- **tailwind-merge** — 클래스 충돌 해소를 위해 검토했으나, `@theme`로 만든 이름을 잘못
  분류하면 화면 전체에서 조용히 스타일이 사라질 수 있어 도입하지 않았다.

## 주요 기능

### 상벌점 (그린마일리지 · 기숙사)
- 규정 **114개**(교내 73 · 기숙사 41) 기반 부여. 반 명단에서 여러 명 한 번에 줄 수 있다
- **취소는 사유가 필수**이고 기록은 남는다 — 합계에서만 빠진다
- 트랙별 집계 규칙이 다르다: 교내는 학년도 단위, 기숙사는 **입학부터 누적**
- 월별 추이·반별 현황·기준 초과 학생 명단 통계
- 생활기록부 근거용 **확인서 인쇄**와 엑셀 내보내기

### 학적·명단
- 엑셀 업로드 → **미리보기 → 확정** 2단계. 무엇이 사라지는지 먼저 보여주고 인원 수를 직접 입력하게 한다
- 학년도 단위 반 편성. 상벌점은 학적이 아니라 **학생 자체에 매달려** 반이 바뀌어도 이력이 이어진다

### 계정·권한
- **초대 기반 가입.** 공개 가입 경로가 없다
- 학생이 직접 학부모 초대코드를 발급한다
- 최초 관리자는 **서버 콘솔에만 찍히는 1회성 토큰**으로 만든다 (사용자 0명일 때만)
- 휴대폰/이메일 확인은 임시로 초대코드 확인 직후 서버 proof를 만든다. 가입 때 proof를 한 번 소진한다

### 감사로그
- 생성·수정·삭제와 **권한 거부(`authz:denied`)까지** 기록
- 행위자·시각·대상·접속 IP를 남기고 화면에서 필터링

## 아키텍처

### 3계층 규칙

```
Route / Server Action   →   Service        →   Repo
  requireAuth()             can() 권한 검사      Prisma 호출만
  zod .safeParse()          업무 로직
  (얇게 유지)                recordAudit()
```

- 라우트·페이지·서버액션에 **업무 로직이나 Prisma 호출을 두지 않는다**
- **zod 검증은 경계에서 한 번만.** 서비스는 타입이 맞는 입력을 신뢰한다
- **`can()`은 서비스 안에서도 부른다.** 화면에서 이미 막았어도 다시 검사한다 (defense-in-depth)
- 세션에서 알아낼 수 있는 식별자는 **절대 클라이언트 입력으로 받지 않는다**
  (`getMyAwards(sessionUser)`는 `studentId`를 인자로 받지 않는다)

### 폴더 구조

```
src/
  core/                 횡단 인프라 — 도메인 로직 없음
    auth/               세션·인증·계정 관리 권한
    authz/              역할(roles) · 권한 판정(can) · 오류(assertCan)
    audit/              recordAudit()
    db/                 Prisma 싱글턴
  modules/<모듈>/        schema(zod) · repo(Prisma) · service(업무 로직)
    merit/              첫 업무 모듈. 새 모듈의 본보기
  app/
    (auth)/             비로그인 — 로그인 · 가입
    (app)/              로그인 필수 — 세션 가드가 레이아웃에 있다
  components/
    ui/                 Button · Badge · DataTable · SectionCard …
    app-shell/          사이드바 · 상단바 · 하단탭 · 모바일 서랍
tests/                  구조를 src/와 맞춘다
```

권한 판정 경로는 **`core/authz/can.ts` 하나뿐**이다. 액션 13개가 유니온 타입으로 선언되어
있어 새 모듈을 추가하면서 등록을 빠뜨리면 테스트가 깨진다.

  색을 못 가리는 사람에게도 형태가 남는다

## 시작하기

필요한 것: **Node 24** (최소 20.12+), **Docker**.

```bash
cp .env.example .env
openssl rand -base64 32        # BETTER_AUTH_SECRET에 넣는다

npm install
npm run db:up                  # Postgres 18 컨테이너 (호스트 5433)
npm run db:migrate             # 스키마 적용
npm run seed:merit             # 상벌점 규정 114개 투입 (1회, 멱등)
npm run dev                    # http://localhost:3000
```

> `npm run seed:merit`은 **설치할 때 한 번만** 돌린다. 규정이 하나라도 있으면 아무것도 하지
> 않으므로 여러 번 돌려도 안전하다. 이후 규정 추가·수정·삭제는 `/admin/merit/rules` 화면에서 한다.

> **설치 후 확인:** 마이그레이션이 2026학년도를 현재 학년도로 심어 둔다. 다른 해에 새로
> 설치하면 `/admin/students`에서 학년도가 맞는지 먼저 확인한다.

### 최초 관리자 만들기

등록된 사용자가 없으면 서버가 뜰 때 콘솔에 1회성 토큰이 찍힌다.

```
────────────────────────────────────────────────────────────────
 등록된 사용자가 없습니다. 최초 관리자를 생성하세요.

   주소: http://localhost:3000/register?token=
   토큰: Xk9f3aQ2...c21b
   (주소 끝에 토큰을 이어 붙여 접속하세요)

 · 이 토큰은 서버를 재시작하면 새로 발급됩니다
 · 계정이 생성되면 즉시 무효화됩니다
────────────────────────────────────────────────────────────────
```

주소와 토큰을 **일부러 다른 줄로 나눈다.** 로그 수집기에 완성된 링크 한 줄로 남으면
자동 링크화 도구에 걸려 클릭 한 번으로 소진될 수 있다.

토큰은 서버 콘솔에만 나오므로 **서버에 접근할 수 있는 사람만** 최초 관리자를 만들 수 있다.
계정이 하나라도 있으면 토큰이 발급되지 않고 `/register`는 거부 화면을 보여준다.

## 명령어

| 명령 | 설명 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm run verify:unit` | 빠른 검증 — `next typegen` 기반 타입체크 + 린트 + 단위 테스트 |
| `npm run verify` | 완전 검증 — 빠른 검증 + 테스트 DB 준비 + 통합 테스트 + 프로덕션 빌드 |

## 테스트

**단위 테스트**는 repo와 감사로그를 목으로 두고 서비스의 권한 판정·업무 로직을 검증한다.
모든 서비스 테스트가 **권한 거부와 감사로그 기록을 함께** 확인한다.

**통합 테스트**는 목으로 검증할 수 없는 것만 실 Postgres에 대고 확인한다 — 트랜잭션 롤백이
실제로 도는지, 초대코드 동시 사용에서 하나만 통과하는지, 유일 제약이 실제로 걸리는지.

```bash
npm run verify:unit         # 빠른 로컬 확인: DB 컨테이너 없이 돈다
npm run db:test:setup       # gbsw_test 생성 (개발 DB와 완전히 분리)
npm run test:integration
npm run verify              # 완전 검증: Docker로 gbsw-db가 떠 있어야 한다
```

개발 DB(`gbsw`)와 **데이터베이스 이름 자체가 다르다.** 통합 테스트가 실 계정·감사로그를
건드릴 수 없게 하는 안전장치다. `npm run verify:unit`은 빠르게 돌리는 기본 확인이고,
`npm run verify`는 Docker의 `gbsw-db` 컨테이너를 전제로 통합 테스트와 `next build`까지 돈다.

## 배포

```bash
docker compose up -d --build
```

`db` → `migrate`(1회성) → `app` 순으로 뜬다. **마이그레이션이 성공해야 앱이 시작된다.**
런타임 이미지를 가볍게 유지하려고 Prisma CLI는 `migrate` 서비스에만 들어 있다.

앱과 DB는 **루프백에만 묶여 있다** — HTTPS는 같은 호스트의 리버스 프록시가 맡는다.
교내 서버에 올리는 절차는 [`docs/deploy.md`](docs/deploy.md)에 있다: 환경변수,
nginx·Caddy 설정, 최초 관리자 만들기, 배포 후 확인 다섯 가지, 백업.

## 알려진 제약

기록해 두고 아직 고치지 않은 것들.

- **명단 확정 화면이 개인정보를 DOM에 담는다.** `/admin/students/import`의 확정 단계는 서버가
  다시 검증할 명단을 hidden input에 JSON으로 싣는다. 서버가 항상 재검증하므로 신뢰 문제는
  아니지만, 오류 리포팅 도구의 DOM 스냅샷에 딸려 나갈 수 있다. 그런 도구를 붙일 때는 이
  화면을 마스킹 대상에 넣는다.
- **감사로그가 접속 IP를 보여주는데 보존 기간 정책이 없다.** IP도 개인정보다. 얼마나 오래
  남길지, 언제 IP만 지울지를 업무 모듈이 늘기 전에 정해야 한다.
- **인증 확인 요청 남용이 감사로그에 안 보인다.** 실제 코드 발송과 임시 즉시 확인 proof
  발급 모두 대상별 5회/시간·IP별 20회/시간 제한이 막기는 하지만, "누가 얼마나
  시도했나"를 나중에 되짚을 자료는 없다.
- **`AcademicYear_single_current` 부분 유니크 인덱스가 마이그레이션 SQL에만 있다.** Prisma가
  표현하지 못해 다음 `migrate dev`가 `DROP INDEX`를 만들 수 있다. 마이그레이션을 새로 만들면
  생성된 SQL을 눈으로 확인한다.
